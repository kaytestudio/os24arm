# Comment style

- Write comments for the next maintainer. Explain why something is done or call out a non-obvious constraint.
- Keep comments short and natural. Don't narrate the code or repeat what the name and implementation already make clear.
- Avoid canned introductions, conversational filler, and claims such as "robust" or "comprehensive".
- Keep useful protocol, hardware, compatibility, and safety details; clarity matters more than making every comment short.
- Leave imported or generated files' comments alone unless changing that code requires it.
